# Free PostgreSQL migration plan (no production changes)

## Goal

Move PetNova account, pet, health-record, and reminder data off Render Free's ephemeral `/tmp/petnova.sqlite3` to a durable managed PostgreSQL database on a $0 plan. This document is a runbook, not permission to access a live database, create an account, or switch production traffic.

## Proposed target

Use a managed PostgreSQL provider with a currently available ongoing free tier, such as [Neon Free](https://neon.com/pricing). At the time this plan was prepared, the provider documents 1 GB storage per project and 100 compute-hours per month; the compute can scale to zero. Recheck the current limits and terms before creating the database. Free plans do not provide a production uptime guarantee, and quotas can suspend connections without deleting data. Keep independent backups.

Do not use Render's free PostgreSQL database for long-term storage because Render documents a 30-day expiration for its free database.

## Hard safety gates — do not skip

1. **Inventory and access:** identify the actual production database path and whether the SQLite file exists in the running instance. Do not assume that the current `/tmp` file contains every record ever created; ephemeral storage may already have lost older data.
2. **Freeze writes for final export:** schedule a short maintenance window and stop account/workspace writes while exporting. Do not copy a live SQLite file with ordinary file copy while it may be writing.
3. **Create an SQLite online backup:** use the repository's `backend/scripts/backup_petnova_db.py` script against a copy of the source database or use SQLite's online backup API. Keep the original unchanged. Store the export locally in a private location, not in GitHub, a public artifact, or a chat message.
4. **Verify the backup before migration:** run SQLite `PRAGMA integrity_check`; record row counts for `users`, `pets`, `health_records`, and `reminders`; record max IDs; check foreign-key consistency. Keep a SHA-256 checksum and at least one separate private copy. Do not proceed if the source file is missing, integrity fails, or counts are uncertain.
5. **Create the target database manually:** create a free PostgreSQL project with the provider dashboard. Keep the connection string private. Store it as a Render environment secret (for example `DATABASE_URL`) only after code support and staging tests are ready. Never commit it.
6. **Implement and test PostgreSQL support off-production:** the current `petnova_data.py` is SQLite-specific. Add a PostgreSQL adapter and migration script on a branch. Translate schema types and generated IDs explicitly; preserve password hashes and timestamps; use parameterized queries; validate transactions and foreign keys. Do not point current SQLite code at a PostgreSQL URL.
7. **Dry-run with a sanitized copy:** migrate a copy containing no real email addresses, passwords, pet notes, or other personal information. Verify row counts, IDs, foreign keys, case-insensitive email uniqueness, login/password verification, and CRUD flows for pets, health records, and reminders.
8. **Production import into an empty target:** take a final verified export during the maintenance window and import once. The import must refuse to run if target tables already contain data unless an explicit, reviewed override is provided. Reset PostgreSQL sequences after importing IDs.
9. **Compare before cutover:** compare counts, IDs, relationships, and representative records from source and target. Do not log passwords, password hashes, auth tokens, or private notes. Keep the old SQLite export and original file untouched.
10. **Cut over reversibly:** configure `DATABASE_URL` and deploy the PostgreSQL-capable backend only after verification. Smoke-test login with a test account, then read-only pet/health/reminder endpoints. Re-enable writes only after tests pass. If checks fail, roll back to the old app/database only if the old data remains available; do not accept writes on two databases concurrently.
11. **Backups and retention:** schedule encrypted exports from PostgreSQL to a private location and periodically test restore. Do not treat a provider's short point-in-time recovery window as the only backup.
12. **After cutover:** retain the SQLite backup until the new system has passed an agreed observation period and a restore drill. Delete personal data from temporary working copies securely when no longer needed.

## Current code constraints

- `backend/app/petnova_data.py` uses `sqlite3`, SQLite `? ` placeholders, `sqlite3.Row`, `INTEGER PRIMARY KEY AUTOINCREMENT`, and SQLite-specific connection setup. A `DATABASE_URL` environment variable alone will not make it PostgreSQL-compatible.
- The database schema has four data tables: `users`, `pets`, `health_records`, and `reminders`.
- Password hashes are PBKDF2-SHA256 strings generated by the application. Preserve the stored hash values exactly; do not export plaintext passwords or force password resets without a deliberate decision.
- Session tokens are signed with `PETNOVA_AUTH_SECRET`. Keep the current secret stable during cutover if you want existing tokens to continue verifying; treat it as a secret and never include it in a backup report.
- Chat/retrieval is separate from this workspace database migration.

## Go/no-go checklist

- [ ] Production SQLite source is located and access is confirmed.
- [ ] Export is complete, integrity-checked, checksummed, and privately backed up.
- [ ] Source row counts and foreign-key checks are recorded.
- [ ] PostgreSQL adapter and migration scripts pass offline CI.
- [ ] Sanitized staging migration and restore test pass.
- [ ] Target counts and relationships match source.
- [ ] Render secrets are configured without exposing credentials.
- [ ] Read-only production smoke checks pass before writes resume.
- [ ] Independent backup and restore procedure is tested.

**Stop condition:** if the live SQLite file is absent, incomplete, or cannot be exported, do not claim that the migration preserves all production records. Recover the best available backup first and document any data gap.
